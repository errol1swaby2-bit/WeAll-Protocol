# First canonical solo-bootstrap finality — F1b design review

**Status:** Open design decision, NON-NORMATIVE. No production consensus change is authorized by this document.  
**Scope:** Draft PR #82, issue #87. Do not treat this note as launch acceptance or an independent security review.  
**Source baseline:** `18f0352ef9a289c70ef4a9a109f59cdd7d79f453` and its subsequent F1b genesis/attestation test commits. Review exact-head CI separately.

## Observed production contracts

1. `scripts/build_production_genesis_manifest.py` produces the height-zero genesis record with one active validator/operator in `roles` and matching validator key registries. It does not predeclare a BFT-active `consensus.validator_set`. The current `configs/genesis.ledger.prod.json` has `height=0`, `finalized=false`, and one genesis role validator. In contrast, the earlier signed-governance F1b fixture starts with an **empty** authoritative consensus active set and cannot establish genesis solo liveness.
2. `runtime/apply/consensus.py::_apply_block_attest` records an attestation against an already-known block/height. `BLOCK_ATTEST` is a validator-origin user transaction. Public ingress and canonical block admission must authenticate its ML-DSA account signature; a direct domain-apply fixture is not signature proof.
3. `runtime/apply/consensus.py::_apply_block_finalize` requires a SYSTEM envelope and a parent. Outside its BFT receipt-driven path, production-default `enforce_finality_attestations` requires more than two-thirds of the active validator set to have a yes attestation. It then updates the canonical finalized record. When it finalizes **height 1**, it enqueues `EPOCH_OPEN(1)` only if epoch 1 is not already established.
4. `runtime/bft_finality_bridge.py::schedule_bft_finality_receipt` currently derives deterministic canonical `BLOCK_FINALIZE` work from an admitted three-chain HotStuff justify-QC, which is available only after BFT activation. The shared normal leader/replay scheduler does not currently derive the **first** solo-bootstrap finalization from an admitted one-validator attestation.
5. `BLOCK_FINALIZE` is a SYSTEM, receipt-only transaction with canonical `parent_tx_type=BLOCK_ATTEST`; `EPOCH_OPEN` is likewise SYSTEM/receipt-only with canonical `parent_tx_type=BLOCK_FINALIZE`. `runtime/system_tx_engine.py` and block build/replay enforce deterministic queue IDs, emission, and same-block `EPOCH_OPEN` lineage witnesses. The initial-finality producer **cannot** simply push a synthetic SYSTEM receipt into a test fixture and call it authorized consensus.
6. `runtime/block_builder.py` and `runtime/block_replay.py` persist **only height, parent ID, and timestamp** under `state["blocks"][block_id]`. `runtime/apply/consensus.py::_apply_block_attest` keeps the target, validator and vote/payload under `state["block_attestations"]`, but **not** the signed source transaction ID, signature or canonical success receipt. Consequently the signed finality parent must be recovered and checked from a separately persisted, actually committed ancestor block body (or through a carefully reviewed, versioned canonical witness-commitment change). Summing the state attestation count without authenticated included-source evidence would not justify first finality.
7. `runtime/constitutional_clock.py::procedure_height` uses optimistic current height when `finalized.height` is zero; `web/src/lib/procedureClock.ts::currentProcedureHeight` can also fall back when a finalized height is zero. `docs/CONSTITUTIONAL_CLOCK.md` specifies finalized height. The exact zero-finality and epoch timing rule needs versioned adjudication before changing consensus or UI behavior.

## Existing positive and negative evidence

- `tests/test_f1b_governance_execute_canonical_two_block.py` covers actual signed proposal/votes, canonical `GOV_EXECUTE -> VALIDATOR_SET_UPDATE`, replayable **pending** four-validator membership, and a noncommitted epoch-activation projection; it also proves another committed block cannot silently activate the pending set.
- `tests/test_p0_03_production_composition.py` covers real four-executor signed HotStuff QC chains, rejected transaction receipt, `BLOCK_FINALIZE`, and restart, but starts from a different fixture-seeded **already active** validator set and transition bridge.
- The new genesis-bootstrap attestation test in the F1b governance test file is intended to prove that the **real genesis builder** can seed a solo validator whose genuine signed `BLOCK_ATTEST` is accepted, canonically committed, follower-replayed, and durable. It explicitly does **not** assert a canonical `BLOCK_FINALIZE` when none is scheduled, and it is not an end-to-end handoff proof. Confirm this claim only after exact-head CI.

## Implemented read-only source resolver (not finality authority)

`runtime/solo_finality_witness.py::resolve_committed_solo_attestation_source` now inspects a previously committed source block body against the canonical ancestry map. It requires an explicitly declared singleton-validator `solo_bootstrap` phase, first-height target, source on the committed tip ancestry path, complete transaction/receipt commitments, an exact positive attestation summary, a successful matching receipt, and a unique source transaction ID. It refuses conflicting top-level/structured signature aliases rather than treating one alias as authoritative. This helper does **not** enqueue, admit, or apply `BLOCK_FINALIZE`, change the constitutional clock, or select the constitutional witness threshold.

The helper relies on the *historical successful canonical inclusion receipt*, which had already passed signed-block admission, rather than improperly verifying historical signing authority against the mutable current account keyset. It is not a standalone cryptographic signature verifier for an untrusted, never-committed candidate. Durable block bodies remain an independent prerequisite: the canonical `state["blocks"]` summary alone still lacks a full signed source envelope and successful receipt. The integration regression also advances to a third committed block and retrieves the earlier signed parent via `get_block_by_id()` on producer, follower, and restarted follower, rather than assuming the parent remains the tip. Source retrieval when a node has only a state-sync snapshot, time/epoch activation, equivocation policy, and BSTR-032 genesis-witness legitimacy remain open.

### Canonical committed-history lookup (read-only)

`runtime/solo_finality_witness.py::resolve_committed_solo_attestation_from_history` now accepts a trusted durable block lookup (for example, `WeAllExecutor.get_block_by_id`) and walks the height-contiguous canonical ancestry from the first target's successor to the committed tip, oldest first. Every encountered committed block body must be retrievable and pass full block/receipt commitment validation against its canonical block ID. No missing body, wrong-ID body, or altered receipt is silently skipped; those fail closed. Source selection refuses more than one successful signed matching attestation across separate committed blocks rather than picking an arbitrary "latest" parent.

The signed-genesis integration regression also proves that a second valid signed `BLOCK_ATTEST` can be committed for the same target under the current apply semantics; the read-only locator consequently refuses this ambiguous source history. This **does not** adjudicate a future rule for duplicate attestations or their finality consequences. The scan is historical preflight and is not wired to the mandatory leader/replay scheduler or any hot-path consensus state mutation. Its linear database reads are not asserted to meet node performance budgets; state-sync snapshots without full historical bodies remain fail-closed until a versioned canonical witness-proof format is approved.

## Candidate to review, NOT an implemented rule

A plausible minimal transition is a **committed-ancestry-derived solo-bootstrap finality scheduler** that verifies the canonical attestation state **against the original signed transaction and successful receipt in a prior committed block**, then uses the existing SYSTEM queue/emitter. The state summary alone is insufficient to identify a signed `BLOCK_ATTEST` parent. It must not introduce a new HotStuff engine, new operator override, or synthetic QC.

The candidate would require **all** of:

- A uniquely authenticated, canonical active singleton validator and explicit solo-bootstrap phase, rather than just a process-local operator setting, untrusted pending set, or bare key registry entry.
- A canonical block at height 1 and a validly ML-DSA-signed `BLOCK_ATTEST` for that exact block/height by that active validator, included in a **previously committed** block and verifiable through independently replayed ancestry. No same-block uncommitted vote may finalize history.
- A deterministic, replay-identical finalizer selection at the first eligible height, monotonic non-conflicting finalized ancestry, strict exact parent/proof binding, and a single `BLOCK_FINALIZE` in the mandatory SYSTEM pre-phase. No direct user/SYSTEM submission substitutes for scheduler provenance.
- Existing `BLOCK_FINALIZE -> EPOCH_OPEN(1)` same-block witness and queue rules; atomic state/root agreement in an independent follower and persistence across restart.
- The resulting validator activation may use only the **already signed and governance-approved** pending four-validator set. It must preserve the exact validator identities, epoch, set hash, transition bridge, and block ancestry that the HotStuff stage later signs.
- Clear exit/fail-closed semantics at the initial finalized epoch boundary; the solo lane must never sign or assert a HotStuff QC and must never be reenabled by environment variables, an operator command, or replay.

## Decisions required before production implementation

1. **Authority and constitutional sufficiency:** Is one verified, signed solo-validator `BLOCK_ATTEST` enough for the first canonical finality, or is a separately committed genesis-witness certificate required? A genesis witness attestation is not automatically the same thing as a validator BLOCK_ATTEST. Candidate v2.0 BSTR-032 specifically requires signed *external genesis-witness* records with household, funding, key-custody and infrastructure independence checks; they are not established by a single validator's transaction and the specification does **not** explicitly declare them interchangeable. BSTR-023/GEN-002 distinguish labeled single-validator genesis from four-validator BFT activation, while GEN-007 forbids height-after-zero exceptional founder privileges.
2. **Parent proof format:** Specify how the finalized target and authenticated attesting transaction are bound to `BLOCK_FINALIZE` (canonical committed attestation transaction ID, signed certificate, or another exact deterministic witness) without inventing a privileged SYSTEM parent. A candidate source proof needs a canonical ancestor block ID, a signed `BLOCK_ATTEST` matching that block's tx ID and signer, a *successful* included receipt for that tx ID, the exact target height/ID, and parent-block ancestry. The current state-root ancestry map contains no full transaction bodies; an emitter must prove a consistent committed-block retrieval path on both producer and follower, including during restart, before enqueueing any receipt.
3. **Epoch timing:** When signed governance completes after some solo blocks, can a delayed first-height finalizer safely activate the pending set at epoch 1, or must governance select a future epoch? Preserve the sequential `EPOCH_OPEN` and no-skipped-epoch rules.
4. **Genesis metadata:** Normalize or explicitly version the difference between the production genesis `finalized=false` placeholder and runtime `finalized={height,block_id}` representation; do not rewrite historical state silently.
5. **Security/Byzantine matrix:** Require failed/forged/nonmember/duplicate/equivocating/stale-key attestation refusal; incorrect signer/chain/block-height/parent/proof refusal; restart, cross-process follower replay, missing-attestation liveness behavior, then actual four-process partitions (3+1, 2+2), conflicting QCs and recovery.
6. **Release gates:** GEN-002 and BSTR-023 in the attached candidate v2.0 specification permit labeled single-validator genesis with **no BFT/decentralization claim**. GEN-007 ends exceptional genesis authority after height zero. These are draft *normative targets*, not already-verified production consensus rules. No post-genesis founder shortcut may be presumed.

## Acceptance rule

Do not close issue #87 or merge PR #82 on test-only projection, synthetic QC, direct ledger edits, quorum bypass, or copied `bft_active` state. The positive gate must prove *one uninterrupted canonical chain* from genesis authority and signed governance to witnessed epoch activation, real signed four-validator 3-chain QCs, canonical rejected receipt/finality, and durable independent-process Byzantine/restart convergence.

**Until the missing finality authority/proof contract is decided, retain DRAFT / NO-GO.**


## Selected engineering ordering: finality first (Option A; 2026-11-06)

**Design-direction decision for draft PR #82, not constitutional ratification or live authority:** use a **finality-first** bootstrap. No governance timer or validator-election approval may be claimed as constitutionally finalized while the finalized constitutional height is still zero. The existing pre-finality signed-governance regression is retained as a *characterization of current code*, not acceptance evidence for this selected sequencing. The historical witness lookup remains read-only until the independent genesis authority certificate and mandatory producer/replay scheduler are reviewed.

The intended *single canonical chain* is ordered as follows:

1. **Height-zero acceptance:** establish an explicit `solo_bootstrap` phase, an unambiguous singleton validator, a versioned and independently reproducible genesis commitment, and an independently signed genesis-acceptance record. Candidate v2.0 `GEN-012` requires at least three external ceremony-witness attestations, with no associated voting/validator authority. `BSTR-032` requires canonical signed records and household, funding, key-custody, and infrastructure independence checks. The acceptance-record serialization, signing domain, commitment placement (without a circular genesis hash), external witness verification and state-sync proof format remain **unapproved and unimplemented**. No post-height-zero founder override is permitted (`GEN-007`).
2. **Solo chain and first finality:** commit height-one block B1, commit the active validator's signed successful `BLOCK_ATTEST(B1)` in a later ancestor (e.g. B2), and independently recover exactly one immutable source transaction plus receipt and complete ancestry on producer and follower. **Only after** satisfying the separate genesis acceptance authority may the future canonical scheduler bind this witness to exactly one mandatory `BLOCK_FINALIZE(B1)` SYSTEM receipt, followed by a properly lineage-bound `EPOCH_OPEN(1)`. Synthetic SYSTEM admission, summary-only attestation counting, historical-body skipping and same-block self-attestation are not authority.
3. **Finalized-height governance:** in epoch 1, run legitimate PoH/role admission, trustee eligibility, constitutional proposals and votes on **finalized procedural time**, not optimistic block height, browser time or the local clock. The candidate v2.0 `BSTR-024` specifies five independent ballot trustees and a valid 3-of-5 ceremony before a ballot opens; the bootstrap does not waive this. Governance must remain live through continuing **authorized solo finalization**. That liveness mechanism, finalized-height-zero migration rule and the scheduler's performance budget remain separate proof obligations.
4. **Future validator-set scheduling:** after a genuinely approved, executed proposal, `VALIDATOR_SET_UPDATE` stages an authenticated four-validator set with `activate_at_epoch` strictly greater than the current epoch. The **earliest candidate activation is epoch 2**, but it must be **epoch 2 or later** as required by real constitutional voting windows, finalized-height epoch boundaries and validator readiness; do not require completion by epoch 2, silently skip epochs, or backdate an already-open epoch. `activate_bft_at_epoch`, when requested, must equal `activate_at_epoch`.
5. **Epoch boundary handoff:** after ordinary authorized epoch-1 close, a canonically queued/replayed `EPOCH_OPEN(activation_epoch)` promotes only the approved pending membership and records the `new_set_qc_over_canonical_boundary` transition bridge. An in-memory `apply_tx` projection tests domain rules **only**; it does not prove committed epoch transitions or constitutional approval. Four separately keyed, separately persisted nodes must then produce real three-of-four signed HotStuff QCs and three-chain finality on the **same** canonical lineage, including restart and Byzantine partition evidence. Solo bootstrap cannot reactivate by operator environment setting.
6. **Deployment claims:** four validator keys are the *minimum BFT activation* gate (candidate `GEN-002`, `BSTR-023`), **not** the candidate seven-validator public-decentralization or thirteen-validator mainnet claim gates. A green F1b four-node rehearsal is not mainnet acceptance.

### Test contract and open blockers

The adjacent regression is a deliberately **projection-only** negative/positive epoch-order check: a height-one post-finality fixture opens epoch 1 without activating four validators; a governance-authorized *fixture* stages epoch-2 activation; a stale epoch-1 update, premature epoch-2 open and missing epoch-1 close must fail; closing epoch 1 then opening epoch 2 activates the precise set with its transition bridge. Its fixture must not be presented as evidence of accepted ceremony signatures, actual signed governance votes, canonical first finality or a four-process deployment.

**No production first-finality scheduler or constitutional clock change is authorized by the selection of Option A alone.** Before wiring them: ratify versioned genesis ceremony/certificate semantics and explicit bootstrap liveness; demonstrate exact genesis source commitments, producer/follower canonical mandatory queue consistency, failure behavior for multiple signed attestation sources, a trustworthy snapshot witness, finalized-height constitutional windows, and uninterrupted signed-governance-to-BFT execution.


## Reference-only external genesis witness signature preflight (2026-11-06)

The isolated module runtime/genesis_acceptance_witness.py is a **cryptographic preflight**, not a genesis acceptance authority rule. It is source-mapped as M-018 / reference_or_test_only and is not imported by the executor, block builder, replay, scheduler, validator-set activation, or BFT voting. It cannot queue BLOCK_FINALIZE or activate consensus.

The candidate v2.0 targets GEN-012 and BSTR-032 require at least three external ceremony witnesses with canonical signed records and independence checks for household, funding, key custody, and infrastructure. The preflight uses a candidate-only weall.genesis-acceptance.preflight.v1 envelope and a disjoint weall.genesis-acceptance.external-witness.preflight.v1 signing domain. Each witness signs the already-frozen genesis *manifest digest*, chain ID, ceremony ID, witness identity, ML-DSA-65 public key, and four SHA-256 private-evidence commitments. The expected manifest digest and original validator key are trusted **separate inputs**; reading them solely from the untrusted receipt would enable substitution. The receipt is separate from the genesis manifest so that witness signatures do not enter a circular genesis hash.

The preflight verifies all signatures (not just the minimum three), rejects duplicate identities and signing keys, rejects using the founder validator key as an "external" witness, and fails closed on changes to signature domain, chain, manifest, ceremony, signer, signature, or evidence commitments. It does not expose raw private evidence, grant a role to witnesses, or treat distinct public keys as proof of independent humans. Signatures over four self-declared commitment digests **do not verify household/funding/key-custody/infrastructure independence**; those facts need an approved evidence-handling and constitutional review process. Its result always carries external_independence_review_required = True and authorizes_first_finality = False.

**Design unresolved:** This candidate is not an adopted ceremony serialization or immutable genesis acceptance certificate. Before using it in a production finality gate, select the external witness identity/independence review authority, define precisely which genesis bytes independent clean-room builds sign, approve the commitment/revocation and evidence-retention model, resolve snapshots without history bodies, pin the schema/domain under constitutional review, and bind the accepted receipt to canonical genesis state without an operator override. No test-only certificate may replace the full authority decision.

## Founding validator key-size correction and manifest binding preflight (2026-11-06)

The production manifest builder previously accepted a 64-hex-character founding validator key (32 bytes) using the same parser as an authority snapshot key identifier. This **cannot be an ML-DSA-65 validator public key**, which requires **1,952 bytes (3,904 hex characters)** under the active `pq-mldsa-v1` signature profile. The repository-pinned `configs/genesis.ledger.prod.json` still contains that legacy 64-hex value, and is therefore **not acceptable as a live ML-DSA signing genesis**. The new builder validation prevents future generation of this malformed founder key and the test proves the rejection. Regenerating the actual production genesis requires an independently verified *real public key* and ceremony; test-generated signing keys must never silently replace the founder's intended key, and changing the genesis changes the genesis hash, state root, and witness signature commitments.

A new **read-only** `preflight_genesis_manifest_witness_binding` checks a caller-provided frozen manifest against an **independently supplied trusted canonical manifest SHA-256**; checks that the exact canonical genesis ledger hashes to the manifest's `genesis_hash` and `genesis_state_root`; requires height zero, empty history/queue, no finalization or BFT phase, a single founding validator, matching validator keys across the account, founding device, node-operator responsibility, bootstrap allowlist, lifecycle and consensus registries; and verifies the genesis protocol and transaction-index hash bindings before checking all three or more external witness signatures. It returns only cryptographic and commitment evidence, with `authorizes_first_finality = False` and mandatory external independence review.

The trusted manifest digest must be obtained from an *independent, reproducible acceptance decision*. It cannot be calculated from an untrusted downloaded manifest and treated as independently trusted merely because it matches its own contents. The production genesis builder does not currently add an explicit `solo_bootstrap` phase or a constitutionally ratified external acceptance certificate to its genesis state; this read-only preflight does not imply either exists. Whether and how an accepted certificate hash is anchored to canonical genesis remains an **unresolved versioned design decision**. No live first-finality queue/scheduler, constitutional governance clock change, validator promotion, or externally accepted genesis was added.


## Independent offline genesis-bundle preflight and same-code reproducibility (2026-11-06)

The next full backend run identified an additional verification mismatch. The old production GO test supplied a 32-byte founder key, while scripts/assert_production_genesis_artifacts.py treated founder signing keys as 64-hex-character hashes, rather than 1,952-byte ML-DSA-65 public keys. The builder now requires the full key, the production assertion script applies the same full-key validation to founding-account records and the bootstrap allowlist, and its distinct 64-hex snapshot-authority and SHA-256 digest fields remain unchanged. A regression uses a real deterministic *test-only* key and proves that a truncated signer key is still rejected even if the genesis hash and state root are recomputed. The pinned legacy production genesis is **not** silently replaced.

The new standalone script scripts/preflight_genesis_witness_bundle.py is **read-only reference verification tooling**, registered as verification tooling under M-076. It accepts frozen genesis ledger JSON, manifest JSON, an external-witness candidate JSON receipt, a separately supplied **out-of-band trusted canonical manifest SHA-256**, and an expected chain ID. It verifies the immutable source and witness signature commitments with the already-reviewed read-only binding helper and emits deterministic JSON indicating *cryptographic_preflight_only*, *reference_only*, *authority_decision=not_performed*, *authorizes_first_finality=false*, and *external_independence_review_required=true*. Duplicate JSON keys, invalid or non-finite JSON, a substituted manifest/ledger, a mismatched trusted digest, and malformed or invalid witness signatures fail closed.

Manual verification syntax (illustrative; placeholders are not trusted evidence):

    python scripts/preflight_genesis_witness_bundle.py \
      --manifest /reviewed/weall-genesis.json \
      --genesis /reviewed/genesis.ledger.prod.json \
      --certificate /reviewed/external-witness-candidate.json \
      --witness-roster /separately-reviewed/external-witness-roster.json \
      --trusted-witness-roster-sha256 REPLACE_WITH_INDEPENDENTLY_VERIFIED_ROSTER_DIGEST \
      --trusted-manifest-sha256 REPLACE_WITH_INDEPENDENTLY_VERIFIED_CANONICAL_DIGEST \
      --expected-chain-id REPLACE_WITH_REVIEWED_CHAIN_ID

Never compute the digest from the untrusted candidate manifest itself and relabel it as independently verified authority. The current ML-DSA-65 signing profile is testnet-capable but explicitly **not approved for mainnet** until external cryptographic review; this reference tool does not override that policy.

The mandatory F1b test rebuilds one frozen-time genesis using identical public inputs in two fresh OS processes and verifies **byte-identical** ledger/manifest outputs, then separately preflights the same signed witness bundle in two fresh interpreters and compares their JSON evidence. This is *same-code reproducibility*, **not** independent clean-room reimplementation, a real externally witnessed constitutional ceremony, nor a live two-validator consensus proof. In particular, separate process execution cannot establish independent witness household, funding, key-custody or infrastructure control.

No genesis acceptance authority, canonical ceremony certificate, first BLOCK_FINALIZE scheduler, constitutional clock change, or BFT transition was added. Production remains gated on accepted GEN-012/BSTR-032 semantics, real signing keys, independent witness evaluation and verifiable first-finality producer/replay scheduling.

## Externally pinned witness identity and signing-key boundary (2026-11-07)

The first signature-only ceremony preflight verified the *cryptographic* signatures of whichever public keys were presented **inside** the candidate genesis certificate. That means an adversary controlling three other keys could produce a fully valid three-signature substitute and receive the same signature-only result. Cryptographic correctness alone cannot bind signatures to the *intended* external witnesses.

The reference-only preflight now additionally requires a **separately supplied, out-of-band trusted witness-roster digest**. A candidate roster has schema `weall.genesis-witness-roster.preflight.v1` and exactly `schema`, `chain_id`, `genesis_manifest_sha256`, `ceremony_id`, and `witnesses` fields. Each `witnesses` entry contains exactly `witness_id` and a **complete ML-DSA-65 public key**. The file may be transported alongside the bundle for convenience, but its expected canonical SHA-256 **must originate independently of the candidate roster and certificate**. Computing a roster SHA from an untrusted file and feeding that same SHA back into the verifier is circular and does not establish an approved roster.

The offline `scripts/preflight_genesis_witness_bundle.py` CLI requires both `--witness-roster` and `--trusted-witness-roster-sha256` in addition to the separately trusted manifest SHA-256 and chain ID. It verifies the underlying immutable genesis manifest, all genuine witness signatures, and *then* binds each signed identity to the externally pinned key for the exact chain, manifest, and ceremony. The whole roster must be represented by successful signed entries; missing, extra, duplicated, founder-reused, substituted or short-key entries fail closed. The new regression includes **three independently valid forged ML-DSA signatures** from replacement witness keys; these pass the old signature check but are refused by the pinned-roster boundary. The two independent Python-process preflights compare identical output with both separate trust anchors.

The resulting status remains `cryptographic_preflight_only`; the roster evidence carries `review_status=independence_review_required` and `authorizes_first_finality=false`. This is a **candidate key-binding format**, not an independently *certified* witness roster, ratified authorization, constitutional acceptance decision, identity-vetting process, or proof of independent households, funding, custody or infrastructure. Different ML-DSA keys can still be controlled by the same human or organization. No witness is granted a PoH tier, validator position or governance vote by appearing in the roster. The roster has no privileged override and is not read by consensus, replay, the block builder or the SYSTEM scheduler.

**Still unresolved before real genesis acceptance:** the constitutional reviewer/registrar identity and qualifications, trusted distribution and approval of the roster digest, verified independence evidence handling, witness replacement/revocation and key-rotation rules, accepted genesis commitment anchoring, crypto profile mainnet approval, and replay/state-sync verification. These need a separate normative choice and independently supplied real signatures, rather than automatically treating a passing preflight as consent or first-finality authority. PR #82 remains draft/NO-GO.
